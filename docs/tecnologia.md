# Tecnologia: Pointspeak

**Tipo de software:** desktop (Windows e Linux), utilitário de bandeja.

## Stack
- **Linguagens:** Rust (edition 2021) e TypeScript (strict).
- **App desktop:** Tauri v2 (`src-tauri/`), com `tauri-plugin-global-shortcut` e ícone na bandeja (feature `tray-icon`).
- **Frontend:** React 18 + Vite + Tailwind CSS v4 (plugin `@tailwindcss/vite`). Uma página por janela: `hud.html` e `settings.html`.
- **Núcleo:** `crates/pointspeak-core`, Rust puro sem dependências de sistema (`serde`, `serde_json`, `thiserror`, `rubato`, `realfft` e `sha2`): máquina de estados do HUD, contrato dos eventos, configuração, lógica do atalho (PTT/Toggle), pipeline de áudio, Model Manager (catálogos ggml e ONNX e download verificado), o contrato da transcrição (trait `Transcriber` e limpeza do texto), o núcleo puro do Whisper em ONNX (log-mel, vocabulário e decodificação gulosa) e a escolha da engine por backend com o fallback para a CPU (whisper.cpp ou a engine ONNX na CPU EP, `engine.rs`).
- **Configuração:** `AppConfig` em `app_config_dir()/config.json` (JSON camelCase; `~/.config/com.pointspeak.app/` no Linux, `%APPDATA%\com.pointspeak.app\` no Windows). Escrita atômica (arquivo `.tmp` + rename). Arquivo ausente ou corrompido carrega os padrões (com log no stderr); campo inválido volta ao padrão e os demais são mantidos. Comandos Tauri: `get_config` e `set_config(config)` (valida, grava e devolve o erro em PT-BR).
- **Eventos backend → HUD:** `hud://state-changed` com `{ state: "idle|recording|transcribing|success|error", message?: string, anchor?: "start|end|center" }` (`message` só no erro, texto curto do `docs/design/DESIGN.md` §3; `anchor` é o `data-anchor` da pílula, reemitido pelo `HudController` quando muda; ausente = manter a última, inicialmente `start`) e `hud://audio-level` com `{ level: 0..1 }`. Constantes e payloads em `pointspeak-core/src/events.rs`.
- **Áudio (em memória, nunca vai para o disco):** `cpal` 0.18 no `src-tauri/src/audio.rs` (ALSA no Linux via `libasound2-dev`, WASAPI no Windows) e `rubato` 5 no núcleo (`pointspeak-core/src/audio.rs`).
  - Captura: `AudioRecorder::from_config(&AppConfig).start(device, on_level, on_auto_stop)` (ou `start_with_classifier(device, Some(classificador do VAD), …)`, que o ditado usa) → `RecordingHandle::stop() -> RecordedAudio` (`samples` 16 kHz mono + `heard_speech`: o detector de silêncio ouviu voz, pelo VAD quando ele está ativo; `None` com a parada por silêncio desligada). `on_auto_stop(Option<StopReason>)` recebe o motivo (`None` = microfone perdido). Usa o formato padrão do dispositivo (f32/i16/u16). O callback do cpal só converte para f32 e faz `try_send` num canal limitado; o processamento roda numa thread própria.
  - Pipeline (`CapturePipeline`): downmix para mono (média) → resample FFT síncrono (`rubato::Fft`, blocos de 1024 quadros, atraso do filtro descartado e resto processado no fim; saída = `ceil(n × 16000 / taxa)`) → RMS a cada 30 ms → `level` 0..1 em escala dB (-60 dB → 0, -10 dB → 1; o `hud://audio-level` continua no RMS) → `SilenceStop` (Silero VAD ou RMS) → buffer limitado a `maxRecordingSecs`.
  - Parada por silêncio (`autoStopOnSilence`, `silenceTimeoutMs`): **Silero VAD** quando o ONNX Runtime e o modelo estão disponíveis, **RMS** de reserva (veja **Silero VAD** abaixo). As duas seguem a mesma regra: só arma depois de 90 ms contínuos de fala e dispara após `silenceTimeoutMs` seguidos de silêncio; fala no meio zera a contagem. Sem relógio real: a duração vem do número de amostras. No RMS (`SilenceDetector`), fala = janela de 30 ms acima de -40 dBFS.
  - Ao atingir `maxRecordingSecs` o buffer para de crescer e o pipeline sinaliza parada; microfone desconectado também chama `on_auto_stop` (e `RecordingHandle::device_lost()` fica `true`).
  - Erros (`AudioError`) viram `ErrorKind::MicrophoneUnavailable` no HUD e texto PT-BR na interface. Comando Tauri `list_microphones` → `[{ name, isDefault }]` (o `name` é o valor de `AppConfig.microphone`).
- **Model Manager (download de modelos):** catálogo, estados e download verificado em `pointspeak-core/src/models.rs` (`sha2`); transporte e comandos em `src-tauri/src/models.rs` (`reqwest` 0.12 blocking com `rustls-tls`/ring, sem OpenSSL nem aws-lc; o Tauri traz o reqwest 0.13 por conta própria).
  - Catálogo: `ggml-tiny.bin`, `ggml-base.bin`, `ggml-small.bin`, `ggml-large-v3-turbo.bin` de `https://huggingface.co/ggerganov/whisper.cpp/resolve/main/<arquivo>`, com tamanho em bytes e SHA-256 tirados do `oid sha256` do LFS (`https://huggingface.co/api/models/ggerganov/whisper.cpp/tree/main`). Textos e tamanhos exibíveis do `DESIGN.md` §4.2; `base` é o recomendado.
  - Pasta: `app_data_dir()/models` (`~/.local/share/com.pointspeak.app/models` no Linux, `%APPDATA%\com.pointspeak.app\models` no Windows). O scan (na inicialização e a cada `list_models`) só confere o tamanho do arquivo; o hash é conferido no download.
  - Download (`download_verified`): consome um `Read`, grava em `<arquivo>.part`, calcula o SHA-256 enquanto grava, avisa o progresso a cada 1 % ou 250 ms, checa a flag de cancelamento a cada bloco de 64 KiB e só renomeia para o nome final com tamanho e hash certos. Em erro ou cancelamento o `.part` é apagado. Mensagens: `Download falhou: conexão perdida` (leitura falhou ou o stream acabou antes), `Arquivo corrompido (SHA-256 não confere)` (hash ou tamanho a mais), `Não foi possível gravar o modelo: …` (disco). Uma thread por download; timeout de 30 s para conectar e para cada leitura.
  - Estados por modelo (`ModelState`, JSON `{ "state": … }`): `notDownloaded`, `downloading` (`done`, `total`), `verifying`, `ready`, `active` (o `AppConfig.model`, se o arquivo existe), `failed` (`reason`).
  - Comandos Tauri: `list_models` → `{ models: [{ id, fileName, sizeBytes, sha256, displaySize, description, recommended, state, done?, total?, reason? }], dir, usedBytes }`; `download_model({ id })` (volta na hora; um por vez por modelo); `cancel_download({ id })`; `remove_model({ id })` (recusa o ativo com "Troque o modelo ativo antes de remover" e o que está baixando); `set_active_model({ id })` (precisa estar `ready`; grava `AppConfig.model` e devolve a config). A pasta abre pelo `open_models_dir` (veja **Janela de Configurações** abaixo).
  - Evento `models://progress` com `{ id, state, done, total, reason? }` a cada mudança (constante e payload em `pointspeak-core/src/events.rs`).
  - Variantes (task #794): os comandos e o evento usam a variante da engine do backend efetivo (ggml para CPU/Vulkan, ONNX para DirectML/OpenVINO/CUDA; veja **Engine Whisper ONNX** abaixo). Veja lá o que muda nos valores.
- **Atalho no Linux (1.3.1, `src-tauri/src/linux_keys.rs`):** o `tauri-plugin-global-shortcut` (crate `global-hotkey`) só funciona no X11; no Wayland ele só recebe teclas com uma janela do app em foco, então o atalho parecia morto (Ubuntu 24.04 usa Wayland por padrão). O app passou a ler os eventos do kernel em `/dev/input/event*` (`struct input_event` de 24 bytes; `EV_KEY`, valor 0/1, a repetição 2 é descartada), uma thread por dispositivo e um rescan a cada 3 s; regra pura no `pointspeak_core::linux_input` (códigos do `input-event-codes.h`, `ComboDetector` com os dois lados dos modificadores e `raw_key` para o `DoubleTapDetector`). Uso: toque duplo (`Ctrl+Ctrl`) no Linux sempre; combinações só no Wayland (`linux_keys::use_for_combos`, pelo `DisplayServer::detect_from_env`); no X11 as combinações continuam no plugin. Precisa do grupo `input` (`sudo usermod -aG input $USER` + entrar de novo); sem ele o registro devolve `RegisterError::Unavailable` com esse texto (não o de conflito), que o `set_config` mostra e o comando `hotkey_status` entrega à seção Atalho (callout `O atalho não está funcionando.`), inclusive quando a falha foi ao abrir o app. Sem captura exclusiva: a tecla também chega ao app em foco.
- **Parakeet TDT 0.6B v3 (1.3.0):** segundo tipo de modelo, `ModelId::ParakeetTdtV3` (`parakeet-tdt-0.6b-v3`; `ModelFamily::Parakeet`). NVIDIA NeMo FastConformer + TDT, multilíngue (25 línguas, com pontuação), licença CC-BY-4.0. Export ONNX INT8 de `istupakov/parakeet-tdt-0.6b-v3-onnx` (commit `8f23f0c0…`), feito para a biblioteca onnx-asr, que serviu de referência da decodificação.
  - Arquivos (`models::PARAKEET_TDT_V3`, pasta `parakeet-tdt-0.6b-v3-int8/`, 640 MB): `nemo128.onnx` (áudio 16 kHz `waveforms [1, N]` + `waveforms_lens` → `features [1, 128, T]`), `encoder-model.int8.onnx` (`audio_signal` + `length` → `outputs [1, 1024, T/8]` + `encoded_lengths`), `decoder_joint-model.int8.onnx` (`encoder_outputs [1, 1024, 1]`, `targets` int32 `[1, 1]`, `target_length` int32, `input_states_1/2 [2, 1, 640]` → `outputs [.., 8198]` = 8193 tokens + 5 durações e `output_states_1/2`) e `vocab.txt` (`<token> <id>`; `▁` = espaço; `<blk>` = 8192).
  - Formato único: não há ggml. `ModelVariant::for_model` leva o Parakeet sempre à variante `Onnx` (pasta, download, remoção, ativação); na lista ggml (CPU) o estado dele vem do registro ONNX (`models::Registries::overview`). O `CATALOG` tem uma linha para ele (nome, tamanho, texto); os arquivos ficam no `PARAKEET_TDT_V3` e as funções `ModelId::onnx_dir_name/onnx_files/onnx_url/onnx_display_size` servem aos dois tipos.
  - Engine: `EngineKind::Parakeet` (o modelo decide, `EnginePlan::kind`), `src-tauri/src/onnx_parakeet.rs` (`ParakeetTranscriber`); regra pura no `pointspeak_core::parakeet` (vocabulário, texto e `tdt_greedy`: a cada frame, o joint devolve token e duração; token ≠ branco é emitido e o estado do LSTM avança; duração 0 fica no frame até 10 tokens). Pré-processador sempre na CPU EP; encoder e joint na CPU EP ou no DirectML (NPU, depois GPU). OpenVINO, CUDA e Vulkan: a carga recusa (`o Parakeet não roda no …`) e o fallback leva à CPU EP; o OpenVINO não roda o encoder INT8 (`Output names mismatch between OpenVINO and ONNX`, NPU e GPU). Áudio acima de 120 s é dividido. A opção de idioma não vale (detecção automática; aviso na seção Idioma).
  - Verificação no DirectML: na 1ª carga em cada dispositivo, a saída do encoder na entrada fixa (`sanity::probe_signal`) é comparada com a da CPU EP (correlação ≥ 0,95, sem NaN) e a aprovação vai para o `verified-devices.json`; depois, só o aquecimento.
  - Medido no Core Ultra X7 358H (13,7 s de fala): CPU EP 0,65 s (texto igual ao da onnx-asr), DirectML (Arc B390) 0,64–0,74 s; 41 s de fala: ~2 s na CPU. RAM em uso: ~830 MB na CPU, ~1,3 GB no DirectML. Carga: ~3–5 s na CPU; 16 s na 1ª vez no DirectML (verificação). Pico estimado: 400 MB + 1,0× arquivos (`memory::load_peak_bytes`). Qualidade: igual ao large-v3-turbo na frase de teste, salvo nomes próprios (`PointSpeak` → `Point Spiac`).
- **Transcrição (whisper.cpp):** contrato em `pointspeak-core/src/transcriber.rs`, engine em `src-tauri/src/transcriber.rs` (`whisper-rs` 0.16 → whisper.cpp 1.8, compilado do fonte pelo `whisper-rs-sys` com cmake e linkado estático).
  - Trait `Transcriber: Send` (`transcribe(&mut self, audio: &[f32], opts) -> Result<String, TranscribeError>` e `name()`), sem nada de whisper: a engine ONNX (`OrtWhisperTranscriber`, task #794) implementa o mesmo. `TranscribeOptions { language: pt|en|auto }` (`TranscribeOptions::from_config`).
  - Quem chama usa `pointspeak_core::transcriber::transcribe(engine, audio, opts)`: áudio vazio ou com menos de 300 ms (4800 amostras a 16 kHz) devolve `""` sem chamar a engine; o texto sai limpo (`clean_text`/`join_segments`: trim, segmentos juntados com espaço, tudo entre `[]` removido — `[BLANK_AUDIO]`, `[Music]`, `[ Silence ]` —, marcadores conhecidos entre `()`/`**` como `(música)`, `(risos)`, `*music*`, notas `♪`, espaços duplos e espaço antes de pontuação). Parênteses de texto normal ficam.
  - Erros (`TranscribeError`, mensagens PT-BR): `NoModelSelected` e `ModelNotFound(caminho)` → `ErrorKind::ModelNotFound`; `Load` e `Inference` → `ErrorKind::TranscriptionFailed`.
  - `WhisperTranscriber::load(caminho)`: confere o arquivo (ausente → `ModelNotFound`), cria o `WhisperContext` e um `WhisperState` reaproveitado em todo ditado. Inferência greedy (`best_of: 1`), `set_language("pt"|"en"|"auto")` (`auto` detecta; `set_detect_language` não é usado porque só detectaria sem transcrever), `no_context`, sem timestamps, `suppress_blank`/`suppress_nst`, threads = `min(núcleos físicos, 8)` (`num_cpus`).
  - Logs: `whisper_rs::install_logging_hooks()` (feature `log_backend`) tira os logs do whisper.cpp/GGML do stdout e os manda para o crate `log`; um logger mínimo do app repassa só avisos e erros ao stderr com o prefixo `[pointspeak]`. Se outro logger for instalado antes (fase de qualidade), ele recebe tudo.
  - Estado: `AppState.transcriber: Mutex<EngineSlot>` (o `EngineSlot` do núcleo guarda o `Option<Box<dyn Transcriber>>` e a `EngineKey` = modelo + backend efetivo; desde a task #794, antes era o caminho do `.bin`). `transcriber::ensure_loaded(app, &config)` carrega no primeiro uso e, se o modelo ativo ou o backend mudou (hot-swap), **libera o contexto antigo antes** de carregar o novo; se o carregamento falhar o slot fica vazio. `transcriber::transcribe(app, &config, &audio)` faz `ensure_loaded` + transcrição. Comando Tauri `load_transcriber` (sem argumentos): pré-carrega o modelo ativo numa thread de bloqueio e devolve o erro em PT-BR (gancho para a pré-carga da fase 4 e para as telas). Carregamento lazy por enquanto; eager/lazy configurável fica para a fase 4.
  - Features do crate `pointspeak` (desligadas por padrão, fora do .exe): `cuda` e `vulkan` (repassam a `whisper-rs/cuda`/`whisper-rs/vulkan` e ligam `use_gpu`). Precisam do CUDA Toolkit / Vulkan SDK na máquina de build.
  - Exemplo: `cargo run -p pointspeak --release --example transcribe -- [--backend <cpu|directml|openvino|cuda>] <modelo.bin | pasta onnx-<id>> <audio.wav> [pt|en|auto]` (padrão `auto` e `cpu`; pasta = engine ONNX, veja **Engine Whisper ONNX**). Lê o WAV com `hound` (dev-dependency; inteiro ou float, qualquer taxa/canais), faz downmix e resample para 16 kHz pelo `pointspeak_core::audio` e imprime o texto no stdout e os tempos no stderr. Em debug o whisper.cpp já sai otimizado (o `whisper-rs-sys` compila em `RelWithDebInfo`), mas use `--release` para medir.
  - Validado (task #765) com `ggml-tiny.bin` e o `samples/jfk.wav` do whisper.cpp (11 s): `en` e `auto` → "And so my fellow Americans ask not what your country can do for you ask what you can do for your country." em ~0,55 s (`en`) e ~1,5 s (`auto`, inclui a detecção) com 8 threads; modelo carregado em ~0,1 s. O mesmo áudio a 48 kHz estéreo deu o mesmo texto (resample do núcleo). Teste real opcional: `POINTSPEAK_TEST_MODEL=… POINTSPEAK_TEST_WAV=… cargo test -p pointspeak --lib whisper_real -- --ignored` (WAV 16 kHz mono i16).
- **HUD que segue o cursor (task #772):** geometria pura em `pointspeak-core/src/hud_layout.rs`, janela em `src-tauri/src/hud.rs` (`HudController`, estado gerenciado do Tauri registrado no `setup`; mostrado/escondido pelo executor do ditado).
  - Unidades: o Tauri 2 dá o cursor (`AppHandle::cursor_position`), os monitores (`available_monitors`: posição, tamanho, `work_area`, `scale_factor`) e posiciona a janela (`set_position(PhysicalPosition)`) em pixels **físicos**. As medidas do design (220 × 56, margem 8, 48 no Wayland) são **lógicas** e são convertidas pelo `scale_factor` do monitor do cursor (`round(lógico × escala)`). Cursor fracionário arredonda para baixo.
  - Regra (DESIGN §3.1): janela em `cursor + 8`; se passar da borda direita da `work_area`, `x = cursor.x − 8 − largura` e âncora `end`; o mesmo em `y` com a altura; no fim a janela é presa dentro da `work_area`. O monitor é o que contém o cursor (`monitor_index_at`), ou o mais próximo; o `monitor_from_point` do Tauri não é usado porque no Linux repassa o ponto ao GDK, que espera coordenadas lógicas.
  - Decisão da API de cursor: só a API do Tauri (sem `x11rb` nem `rdev`). No X11 o tao lê o ponteiro pelo GDK; no Windows pelo `GetCursorPos`. A crate `windows` 0.62 (a mesma do Tauri, só em `cfg(windows)`) entra só para mostrar sem ativar.
  - Rastreio: uma thread (`pointspeak-hud-tracker`) criada no primeiro `show()`, chama o tick a cada 16 ms (~60 Hz) enquanto o HUD está visível e fica estacionada em `thread::park` quando escondido (sem girar). A lista de monitores é relida a cada 1 s durante o rastreio; a janela só é movida quando a posição muda.
  - Foco e click-through: `focusable: false` vira `accept_focus(false)` no GTK (X11 não dá foco no `show()`) e `WS_EX_NOACTIVATE` no Windows. Mas o `show()` do tao no Windows usa `ShowWindow(SW_SHOW)`, que ativa; por isso no Windows o HUD é mostrado com `ShowWindow(SW_SHOWNOACTIVATE)` + `SetWindowPos(HWND_TOPMOST, SWP_NOACTIVATE)` e escondido com `SW_HIDE`, direto no hwnd (nunca pelo `show()`/`hide()` do Tauri, cuja flag interna fica "escondida"). Click-through: `set_ignore_cursor_events(true)` (no Windows antes de mostrar; no Linux depois, porque o tao precisa do `GdkWindow` já realizado).
  - Wayland (`DisplayServer::detect_from_env`: `WAYLAND_DISPLAY` ou `XDG_SESSION_TYPE`; o `GDK_BACKEND` não conta): sem posição global do cursor (o tao devolve `(0, 0)`). O HUD é posto uma vez no `show()`, no centro-inferior da `work_area` do monitor principal, sem rastreio.
  - Foco no Wayland (1.3.1): no GNOME toda janela Wayland nova ganha o foco (o `accept_focus(false)` do GTK só vale no X11), então ao começar a gravar o HUD tirava o foco do campo onde a pessoa ia ditar (reproduzido no Ubuntu 24.04/GNOME 46 com uma janela de teste que registra `focus-out`). Por isso, numa sessão Wayland com XWayland (`DISPLAY`), o `run()` põe `GDK_BACKEND=x11` antes do GTK (`hud_layout::gtk_backend_override`; não mexe num `GDK_BACKEND` já escolhido; `POINTSPEAK_NATIVE_WAYLAND=1` desliga): as janelas do app vão para o XWayland, onde o HUD aparece sem foco (confirmado no mesmo teste). A sessão continua Wayland para a colagem (`wtype`), o atalho (`/dev/input`) e o HUD fixo (no XWayland o cursor só é conhecido sobre janelas X11).
- **Injeção de texto (task #773):** regras puras em `pointspeak-core/src/injector.rs`, efeito em `src-tauri/src/injector.rs` (`injector::inject(texto, display) -> Result<(), InjectError>`; chamado pelo executor do ditado numa thread `pointspeak-inject`).
  - Dependências: `arboard` 3.7 (clipboard de texto e imagem; no Linux via X11/XWayland, sem a feature `wayland-data-control`), `enigo` 0.6 (teclas; no Linux o backend padrão `x11rb`/XTest, sem libxdo; o `xkbcommon` dele linka a `libxkbcommon`, agora no `setup-linux.sh`), `x11rb` 0.13 só no Linux (janela ativa) e as features `Win32_System_Threading` da crate `windows` (processo da janela em primeiro plano).
  - Sequência (spec §4.6, `paste_preserving_clipboard` sobre o trait `ClipboardLike`): texto vazio ou só espaços não cola nem toca o clipboard → guarda o clipboard (texto; senão imagem RGBA; senão "vazio") → põe o texto e **lê de volta para conferir** (`paste_preserving_clipboard_retrying`; Windows: até 5 tentativas com 20 ms entre elas, porque outro processo pode estar com o clipboard aberto; Linux: 1) → cola → espera `restore_delay(os)` (**Windows 400 ms**, Linux 50 ms; o SendInput é assíncrono e o app em foco lê o clipboard depois da tecla, então com 50 ms colava o texto antigo) → restaura (vazio = limpa). Se o clipboard não ficar com o texto transcrito, **nada é colado** (colaria o conteúdo antigo): o original é restaurado e vem `PasteError::SetText` → `InjectError::Clipboard` no HUD. **Colagem falhou:** tenta restaurar o clipboard original antes de devolver `ErrorKind::PasteFailed` ("Falha ao colar"); falha ao restaurar após colagem bem-sucedida conta como sucesso, com aviso no log.
  - Atalho (`paste_keys_for`): Shift+Insert se o app em foco é um terminal da lista fixa `TERMINALS` (comparação sem maiúsculas: gnome-terminal(-server), konsole, xterm, alacritty, kitty, wezterm/org.wezfurlong.wezterm, terminator, tilix, xfce4-terminal, urxvt/rxvt, foot, WindowsTerminal.exe, cmd.exe, conhost.exe, powershell.exe, pwsh.exe, mintty.exe); qualquer outro app ou nada detectado → Ctrl+V. App em foco: Windows `GetForegroundWindow` → `GetWindowThreadProcessId` → `QueryFullProcessImageNameW` (nome do executável); X11 `_NET_ACTIVE_WINDOW` → `WM_CLASS` (instância e classe); Wayland não detecta.
  - Métodos por servidor gráfico (`paste_strategy`, o primeiro que funcionar vale): Windows e X11 = enigo (SendInput / XTest; Ctrl+V usa a tecla virtual V no Windows e o keysym `v` no X11); Wayland = teclado virtual do próprio app (`PasteMethod::Uinput`, `src-tauri/src/linux_uinput.rs`, 1.3.1: cria "PointSpeak virtual keyboard" no `/dev/uinput` na abertura do app e manda `injector::paste_key_events`: Ctrl+V = 29↓ 47↓ 47↑ 29↑, Shift+Insert = 42↓ 110↓ 110↑ 42↑, 12 ms entre eventos; enquanto cola, `linux_input`/`linux_keys` ignoram as teclas para o `Ctrl` não contar como toque do `Ctrl+Ctrl`; o .deb instala `70-pointspeak-uinput.rules`, que dá ao grupo `input` o `/dev/uinput`, e um `postinst` que aplica a regra sem reiniciar; motivo: no GNOME o `wtype` falha com `Compositor does not support the virtual keyboard protocol` e o `ydotool` do Ubuntu 24.04 é o 0.1.8, de sintaxe antiga; testado ponta a ponta no Ubuntu 24.04/GNOME 46 com um microfone virtual do PipeWire tocando a fala de teste: texto colado no campo em foco e clipboard restaurado) → `wtype -M ctrl v -m ctrl` (Shift+Insert: `-M shift -k Insert -m shift`) → `ydotool key 29:1 47:1 47:0 29:0` (Shift+Insert: `42:1 110:1 110:0 42:0`) → enigo (só alcança apps do XWayland). `wtype`/`ydotool` são procurados no `PATH`; ausente ou saída com erro passa ao próximo, e o erro final junta os motivos.
  - Thread: arboard e enigo bloqueiam, então tudo roda na thread `pointspeak-injector` (criada na primeira chamada; `inject` manda o trabalho por canal e espera a resposta, então chame fora da thread principal). Ela mantém o `Clipboard` e o `Enigo` vivos: no X11 o conteúdo do clipboard só existe enquanto o processo que o pôs o serve.
  - **Limitações:** conteúdo do clipboard que não é texto nem imagem (arquivos copiados, HTML/RTF sem texto puro) não é guardado e o clipboard fica vazio depois da colagem; texto com formatação volta só como texto puro. ## Segurança e privacidade
Revisão da task #807 (achados e o que ficou de fora na ficha da task). Garantias que o código mantém:

- **Nada do ditado sai da máquina nem vai para log.** O áudio fica só em memória (`audio.rs`: canal limitado → `RecordingBuffer` com teto de `max_recording_secs`, no máximo 3600 s ≈ 230 MB de f32) e é solto depois da inferência; não há gravação em disco. O texto transcrito e o conteúdo do clipboard nunca entram em `eprintln!`/`log::` (os erros de colagem e de inferência só levam o motivo) nem em evento (o `hud://state-changed` leva só o estado e a mensagem de erro). A única rede do app é o download dos modelos; não há telemetria.
- **Modo `clipboard`:** o texto ditado substitui o clipboard e fica lá até o usuário copiar outra coisa (nada é restaurado); continua marcado para ficar fora do histórico (Win+V/nuvem), então não aparece nele. Qualquer app que leia o clipboard vê o texto.
- **Clipboard do usuário:** guardado (texto ou imagem) antes de colar e restaurado depois do atraso por plataforma (400 ms no Windows, 50 ms no Linux), também quando a colagem falha (`paste_preserving_clipboard`). Cancelar ou errar antes da colagem não toca o clipboard. O texto ditado é marcado para ficar fora do histórico do clipboard (Windows: Win+V e nuvem; Linux: `x-kde-passwordManagerHint`, respeitado pelo Klipper e outros), pelo `SetExtWindows`/`SetExtLinux` do arboard.
- **Downloads de modelo:** URLs fixas em HTTPS (`huggingface.co`, ONNX num commit fixado), `reqwest` com rustls. Cada arquivo é gravado em `.part`, com o tamanho limitado ao do catálogo (byte a mais = corrompido) e o SHA-256 conferido antes do `rename`; `.part` nunca é carregado. Os comandos recebem o modelo como `ModelId` (enum), então não há caminho vindo da interface nem path traversal na pasta dos modelos. O atalho (`Accelerator::parse`) e os limites numéricos são validados no `set_config`.
- **Superfície da interface:** CSP `default-src 'self'` (estilos inline liberados para o React) e permissões por janela: os comandos do app são declarados no `build.rs`, a capability `settings` libera `core:default` e os comandos, a `hud` só `listen`/`unlisten` de eventos (o HUD não invoca comando nem mexe em janela).
- **Scripts de build:** `fetch-onnxruntime.sh` baixa versões fixas e confere o SHA-256 de cada pacote; nenhum script faz `curl | sh`.
- **Robustez:** pânico na thread de inferência ou de colagem vira erro no HUD (o ditado não fica preso em "Transcrevendo…"); a thread do injector sobrevive a um pânico; locks envenenados seguem com o valor (sem `unwrap()` de `Mutex` fora dos testes). Pânico na thread de áudio devolve áudio vazio (o HUD mostra "sem fala"); falha do VAD cai para o RMS.
- **Desempenho ocioso:** sem polling com o app parado: o rastreio do cursor só roda com o HUD visível (thread estacionada com `park`), o executor do ditado e o injector esperam em canal, o timer do HUD só corre gravando. O callback do `cpal` não bloqueia (`try_send`; bloco descartado se a fila de ~5 s encher) e a fila do VAD é limitada. O hot-swap solta a engine antiga antes de carregar a nova.

Riscos aceitos:

- **Busca do ONNX Runtime:** `ORT_DYLIB_PATH` → `resource_dir` → pasta do executável. Quem controla o ambiente do usuário consegue carregar outra biblioteca pela variável; isso pressupõe acesso à conta, então é aceito (a variável existe para desenvolvimento). Caminho relativo na variável é ignorado (seria resolvido pela pasta atual). No Windows o `DirectML.dll` é pré-carregado da pasta do `onnxruntime.dll` (não o antigo do System32); as demais dependências do ONNX Runtime seguem a ordem de busca padrão do Windows, que começa pela pasta do executável. O instalador NSIS é por usuário, então a pasta da instalação é gravável pelo próprio usuário (como em todo app instalado por usuário).
- **Clipboard compartilhado por 400 ms (Windows) / 50 ms (Linux):** outro app que leia o clipboard nesse intervalo vê o texto ditado; gerenciadores que ignoram as dicas de histórico podem guardá-lo.
- **Callback do `cpal`** aloca um `Vec<f32>` por bloco (conversão de formato): não bloqueia, mas não é livre de alocação.
- **Sem assinatura** do instalador nem dos pacotes Linux; integridade só pelo canal de distribuição.

## Como rodar os testes
Na ordem (o `dist/` do `npm run build` é exigido pelo `generate_context!` do Tauri ao compilar o Rust):

```sh
npm ci
npm run lint
npm test                 # no runner: RUNNER_TEST_MAX_WORKERS=2 npm test
npm run build            # tsc --noEmit && vite build
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

- Primeira compilação com o whisper.cpp (task #765, 8 núcleos, `target/` vazio): `cargo build --workspace --all-targets` ~1 min 40 s (o whisper.cpp sai otimizado mesmo em debug); `target/debug` passa a ~7,6 GB. Os checks continuam terminando sozinhos: nenhum teste carrega modelo (o teste real é `#[ignore]`).
- Testes afetados enquanto itera: `npx vitest run --changed origin/main`; só o núcleo: `cargo test -p pointspeak-core`.
- Testes de integração do núcleo (`crates/pointspeak-core/tests/`) cobrem áudio sintético até ditado/transcrição/colagem, config/modelos, fallbacks e clipboard falso; não usam tela, microfone, rede, modelos ou ONNX Runtime.
- O contrato Rust↔TypeScript fica em `src/test/fixtures/rust-contracts.json`. `cargo test --workspace` compara a fixture serializada; o Vitest a lê em `src/test/rust-contract.test.tsx` e exercita HUD e Settings. Para regenerar após revisar uma mudança intencional de contrato: `cargo test -p pointspeak-core --test contract_fixtures write_rust_contract_fixtures -- --ignored`.
- O `vite.config.ts` lê `RUNNER_TEST_MAX_WORKERS` (número ou percentual; padrão `50%`).
- Nenhum teste usa tela, microfone ou rede.
