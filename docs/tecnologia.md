# Tecnologia: Pointspeak

**Tipo de software:** desktop (Windows e Linux), utilitário de bandeja.

## Stack
- **Linguagens:** Rust (edition 2021) e TypeScript (strict).
- **App desktop:** Tauri v2 (`src-tauri/`), com `tauri-plugin-global-shortcut` e ícone na bandeja (feature `tray-icon`).
- **Frontend:** React 18 + Vite + Tailwind CSS v4 (plugin `@tailwindcss/vite`). Uma página por janela: `hud.html` e `settings.html`.
- **Núcleo:** `crates/pointspeak-core`, Rust puro sem dependências de sistema (`serde`, `thiserror`, `rubato` e `sha2`): máquina de estados do HUD, contrato dos eventos, configuração, lógica do atalho (PTT/Toggle), pipeline de áudio, Model Manager (catálogo e download verificado) e o contrato da transcrição (trait `Transcriber` e limpeza do texto).
- **Configuração:** `AppConfig` em `app_config_dir()/config.json` (JSON camelCase; `~/.config/com.pointspeak.app/` no Linux, `%APPDATA%\com.pointspeak.app\` no Windows). Escrita atômica (arquivo `.tmp` + rename). Arquivo ausente ou corrompido carrega os padrões (com log no stderr); campo inválido volta ao padrão e os demais são mantidos. Comandos Tauri: `get_config` e `set_config(config)` (valida, grava e devolve o erro em PT-BR).
- **Eventos backend → HUD:** `hud://state-changed` com `{ state: "idle|recording|transcribing|success|error", message?: string, anchor?: "start|end|center" }` (`message` só no erro, texto curto do `docs/design/DESIGN.md` §3; `anchor` é o `data-anchor` da pílula, reemitido pelo `HudController` quando muda; ausente = manter a última, inicialmente `start`) e `hud://audio-level` com `{ level: 0..1 }`. Constantes e payloads em `pointspeak-core/src/events.rs`.
- **Áudio (em memória, nunca vai para o disco):** `cpal` 0.18 no `src-tauri/src/audio.rs` (ALSA no Linux via `libasound2-dev`, WASAPI no Windows) e `rubato` 5 no núcleo (`pointspeak-core/src/audio.rs`).
  - Captura: `AudioRecorder::from_config(&AppConfig).start(device, on_level, on_auto_stop)` → `RecordingHandle::stop() -> Vec<f32>` (16 kHz, mono). Usa o formato padrão do dispositivo (f32/i16/u16). O callback do cpal só converte para f32 e faz `try_send` num canal limitado; o processamento roda numa thread própria.
  - Pipeline (`CapturePipeline`): downmix para mono (média) → resample FFT síncrono (`rubato::Fft`, blocos de 1024 quadros, atraso do filtro descartado e resto processado no fim; saída = `ceil(n × 16000 / taxa)`) → RMS a cada 30 ms → `level` 0..1 em escala dB (-60 dB → 0, -10 dB → 1) → `SilenceDetector` → buffer limitado a `maxRecordingSecs`.
  - Parada por silêncio (`autoStopOnSilence`): limiar fixo de -40 dBFS de RMS por janela; só arma depois de 90 ms contínuos acima do limiar (houve fala) e dispara após `silenceTimeoutMs` seguidos abaixo dele. Sem relógio real: a duração vem do número de amostras. O Silero VAD substitui isso na fase 6.
  - Ao atingir `maxRecordingSecs` o buffer para de crescer e o pipeline sinaliza parada; microfone desconectado também chama `on_auto_stop` (e `RecordingHandle::device_lost()` fica `true`).
  - Erros (`AudioError`) viram `ErrorKind::MicrophoneUnavailable` no HUD e texto PT-BR na interface. Comando Tauri `list_microphones` → `[{ name, isDefault }]` (o `name` é o valor de `AppConfig.microphone`).
- **Model Manager (download de modelos):** catálogo, estados e download verificado em `pointspeak-core/src/models.rs` (`sha2`); transporte e comandos em `src-tauri/src/models.rs` (`reqwest` 0.12 blocking com `rustls-tls`/ring, sem OpenSSL nem aws-lc; o Tauri traz o reqwest 0.13 por conta própria).
  - Catálogo: `ggml-tiny.bin`, `ggml-base.bin`, `ggml-small.bin`, `ggml-large-v3-turbo.bin` de `https://huggingface.co/ggerganov/whisper.cpp/resolve/main/<arquivo>`, com tamanho em bytes e SHA-256 tirados do `oid sha256` do LFS (`https://huggingface.co/api/models/ggerganov/whisper.cpp/tree/main`). Textos e tamanhos exibíveis do `DESIGN.md` §4.2; `base` é o recomendado.
  - Pasta: `app_data_dir()/models` (`~/.local/share/com.pointspeak.app/models` no Linux, `%APPDATA%\com.pointspeak.app\models` no Windows). O scan (na inicialização e a cada `list_models`) só confere o tamanho do arquivo; o hash é conferido no download.
  - Download (`download_verified`): consome um `Read`, grava em `<arquivo>.part`, calcula o SHA-256 enquanto grava, avisa o progresso a cada 1 % ou 250 ms, checa a flag de cancelamento a cada bloco de 64 KiB e só renomeia para o nome final com tamanho e hash certos. Em erro ou cancelamento o `.part` é apagado. Mensagens: `Download falhou: conexão perdida` (leitura falhou ou o stream acabou antes), `Arquivo corrompido (SHA-256 não confere)` (hash ou tamanho a mais), `Não foi possível gravar o modelo: …` (disco). Uma thread por download; timeout de 30 s para conectar e para cada leitura.
  - Estados por modelo (`ModelState`, JSON `{ "state": … }`): `notDownloaded`, `downloading` (`done`, `total`), `verifying`, `ready`, `active` (o `AppConfig.model`, se o arquivo existe), `failed` (`reason`).
  - Comandos Tauri: `list_models` → `{ models: [{ id, fileName, sizeBytes, sha256, displaySize, description, recommended, state, done?, total?, reason? }], dir, usedBytes }`; `download_model({ id })` (volta na hora; um por vez por modelo); `cancel_download({ id })`; `remove_model({ id })` (recusa o ativo com "Troque o modelo ativo antes de remover" e o que está baixando); `set_active_model({ id })` (precisa estar `ready`; grava `AppConfig.model` e devolve a config). `open_models_dir` fica para a fase das telas.
  - Evento `models://progress` com `{ id, state, done, total, reason? }` a cada mudança (constante e payload em `pointspeak-core/src/events.rs`).
- **Transcrição (whisper.cpp):** contrato em `pointspeak-core/src/transcriber.rs`, engine em `src-tauri/src/transcriber.rs` (`whisper-rs` 0.16 → whisper.cpp 1.8, compilado do fonte pelo `whisper-rs-sys` com cmake e linkado estático).
  - Trait `Transcriber: Send` (`transcribe(&mut self, audio: &[f32], opts) -> Result<String, TranscribeError>` e `name()`), sem nada de whisper: a engine `ort` da fase 6 implementa o mesmo. `TranscribeOptions { language: pt|en|auto }` (`TranscribeOptions::from_config`).
  - Quem chama usa `pointspeak_core::transcriber::transcribe(engine, audio, opts)`: áudio vazio ou com menos de 300 ms (4800 amostras a 16 kHz) devolve `""` sem chamar a engine; o texto sai limpo (`clean_text`/`join_segments`: trim, segmentos juntados com espaço, tudo entre `[]` removido — `[BLANK_AUDIO]`, `[Music]`, `[ Silence ]` —, marcadores conhecidos entre `()`/`**` como `(música)`, `(risos)`, `*music*`, notas `♪`, espaços duplos e espaço antes de pontuação). Parênteses de texto normal ficam.
  - Erros (`TranscribeError`, mensagens PT-BR): `NoModelSelected` e `ModelNotFound(caminho)` → `ErrorKind::ModelNotFound`; `Load` e `Inference` → `ErrorKind::TranscriptionFailed`.
  - `WhisperTranscriber::load(caminho)`: confere o arquivo (ausente → `ModelNotFound`), cria o `WhisperContext` e um `WhisperState` reaproveitado em todo ditado. Inferência greedy (`best_of: 1`), `set_language("pt"|"en"|"auto")` (`auto` detecta; `set_detect_language` não é usado porque só detectaria sem transcrever), `no_context`, sem timestamps, `suppress_blank`/`suppress_nst`, threads = `min(núcleos físicos, 8)` (`num_cpus`).
  - Logs: `whisper_rs::install_logging_hooks()` (feature `log_backend`) tira os logs do whisper.cpp/GGML do stdout e os manda para o crate `log`; um logger mínimo do app repassa só avisos e erros ao stderr com o prefixo `[pointspeak]`. Se outro logger for instalado antes (fase de qualidade), ele recebe tudo.
  - Estado: `AppState.transcriber: Mutex<EngineSlot>` (o `EngineSlot` do núcleo guarda o `Option<Box<dyn Transcriber>>` e o caminho do modelo carregado). `transcriber::ensure_loaded(app, &config)` carrega no primeiro uso e, se o modelo ativo mudou (hot-swap), **libera o contexto antigo antes** de carregar o novo; se o carregamento falhar o slot fica vazio. `transcriber::transcribe(app, &config, &audio)` faz `ensure_loaded` + transcrição. Comando Tauri `load_transcriber` (sem argumentos): pré-carrega o modelo ativo numa thread de bloqueio e devolve o erro em PT-BR (gancho para a pré-carga da fase 4 e para as telas). Carregamento lazy por enquanto; eager/lazy configurável fica para a fase 4.
  - Features do crate `pointspeak` (desligadas por padrão, fora do .exe): `cuda` e `vulkan` (repassam a `whisper-rs/cuda`/`whisper-rs/vulkan` e ligam `use_gpu`). Precisam do CUDA Toolkit / Vulkan SDK na máquina de build.
  - Exemplo: `cargo run -p pointspeak --release --example transcribe -- <modelo.bin> <audio.wav> [pt|en|auto]` (padrão `auto`). Lê o WAV com `hound` (dev-dependency; inteiro ou float, qualquer taxa/canais), faz downmix e resample para 16 kHz pelo `pointspeak_core::audio` e imprime o texto no stdout e os tempos no stderr. Em debug o whisper.cpp já sai otimizado (o `whisper-rs-sys` compila em `RelWithDebInfo`), mas use `--release` para medir.
  - Validado (task #765) com `ggml-tiny.bin` e o `samples/jfk.wav` do whisper.cpp (11 s): `en` e `auto` → "And so my fellow Americans ask not what your country can do for you ask what you can do for your country." em ~0,55 s (`en`) e ~1,5 s (`auto`, inclui a detecção) com 8 threads; modelo carregado em ~0,1 s. O mesmo áudio a 48 kHz estéreo deu o mesmo texto (resample do núcleo). Teste real opcional: `POINTSPEAK_TEST_MODEL=… POINTSPEAK_TEST_WAV=… cargo test -p pointspeak --lib whisper_real -- --ignored` (WAV 16 kHz mono i16).
- **HUD que segue o cursor (task #772):** geometria pura em `pointspeak-core/src/hud_layout.rs`, janela em `src-tauri/src/hud.rs` (`HudController`, estado gerenciado do Tauri registrado no `setup`; ainda sem atalho).
  - Unidades: o Tauri 2 dá o cursor (`AppHandle::cursor_position`), os monitores (`available_monitors`: posição, tamanho, `work_area`, `scale_factor`) e posiciona a janela (`set_position(PhysicalPosition)`) em pixels **físicos**. As medidas do design (220 × 56, margem 8, 48 no Wayland) são **lógicas** e são convertidas pelo `scale_factor` do monitor do cursor (`round(lógico × escala)`). Cursor fracionário arredonda para baixo.
  - Regra (DESIGN §3.1): janela em `cursor + 8`; se passar da borda direita da `work_area`, `x = cursor.x − 8 − largura` e âncora `end`; o mesmo em `y` com a altura; no fim a janela é presa dentro da `work_area`. O monitor é o que contém o cursor (`monitor_index_at`), ou o mais próximo; o `monitor_from_point` do Tauri não é usado porque no Linux repassa o ponto ao GDK, que espera coordenadas lógicas.
  - Decisão da API de cursor: só a API do Tauri (sem `x11rb` nem `rdev`). No X11 o tao lê o ponteiro pelo GDK; no Windows pelo `GetCursorPos`. A crate `windows` 0.62 (a mesma do Tauri, só em `cfg(windows)`) entra só para mostrar sem ativar.
  - Rastreio: uma thread (`pointspeak-hud-tracker`) criada no primeiro `show()`, chama o tick a cada 16 ms (~60 Hz) enquanto o HUD está visível e fica estacionada em `thread::park` quando escondido (sem girar). A lista de monitores é relida a cada 1 s durante o rastreio; a janela só é movida quando a posição muda.
  - Foco e click-through: `focusable: false` vira `accept_focus(false)` no GTK (X11 não dá foco no `show()`) e `WS_EX_NOACTIVATE` no Windows. Mas o `show()` do tao no Windows usa `ShowWindow(SW_SHOW)`, que ativa; por isso no Windows o HUD é mostrado com `ShowWindow(SW_SHOWNOACTIVATE)` + `SetWindowPos(HWND_TOPMOST, SWP_NOACTIVATE)` e escondido com `SW_HIDE`, direto no hwnd (nunca pelo `show()`/`hide()` do Tauri, cuja flag interna fica "escondida"). Click-through: `set_ignore_cursor_events(true)` (no Windows antes de mostrar; no Linux depois, porque o tao precisa do `GdkWindow` já realizado).
  - Wayland (`DisplayServer::detect_from_env`: `GDK_BACKEND` primeiro, depois `WAYLAND_DISPLAY`, depois `XDG_SESSION_TYPE`): sem posição global do cursor (o tao devolve `(0, 0)`). O HUD é posto uma vez no `show()`, no centro-inferior da `work_area` do monitor principal, sem rastreio. **Limitação:** janela comum (sem layer-shell), o compositor pode ignorar a posição pedida. Com `GDK_BACKEND=x11` o app roda no XWayland e segue o cursor (só enquanto ele está sobre janelas X11).
- **Planejado para as próximas fases** (ainda não adicionado): `ort` (ONNX Runtime, NPU/DirectML), `arboard` + `enigo` (+ `wtype`/`ydotool` no Wayland).
- **Testes:** `cargo test` + `clippy` + `rustfmt` (`tempfile` como dev-dependency do núcleo e do `src-tauri` para testar a persistência e o download; `hound` no `src-tauri` para o exemplo e o teste `#[ignore]` da transcrição real); a transcrição é testada com o `FakeTranscriber` do núcleo, sem modelo; Vitest + Testing Library (jsdom), com mock de `@tauri-apps/api` em `src/test/tauri-mock.ts`.
- **Lint:** ESLint flat config (`eslint.config.js`) com typescript-eslint e react-hooks, sem warnings.
- **Infra (Windows):** compilação cruzada com `cargo-xwin` + target `x86_64-pc-windows-msvc` + NSIS + lld/llvm, gerando o instalador `.exe` (veja **Instalador Windows** abaixo).
- **Toolchain:** `rust-toolchain.toml` usa o canal `stable` e garante os componentes `rustfmt` e `clippy`.

## Setup (Linux, Debian/Ubuntu)
1. Rust via rustup e Node.js 22 com npm.
2. `./scripts/setup-linux.sh`: instala webkit2gtk-4.1, gtk3, appindicator, librsvg, alsa, xdo, ssl, x11/xcb, pkg-config, build-essential, cmake, clang/libclang. Idempotente: sem pacote faltando, não chama o `apt-get`.
3. `npm ci`.

## Como rodar
- App em desenvolvimento: `npm run tauri dev` (Vite na porta 1420).
- Binário Linux: `npm run build && cargo build -p pointspeak`.
- Pacotes (deb/AppImage): `npm run tauri build`.

## Instalador Windows (.exe NSIS, compilação cruzada)
O instalador Windows sai deste Linux pelo caminho documentado do Tauri v2 (cargo-xwin + `x86_64-pc-windows-msvc` + NSIS). Não entra nos checks (pesado demais); rode nas etapas que mexem em dependência nativa e no empacotamento.

1. Pré-requisitos (uma vez por máquina, depois do `setup-linux.sh`): `./scripts/setup-windows-cross.sh`. Idempotente: instala `nsis lld llvm clang clang-19 ninja-build` pelo apt, `rustup target add x86_64-pc-windows-msvc` e `cargo install --locked cargo-xwin`.
2. Gerar: `./scripts/build-windows.sh`. Põe `/usr/lib/llvm-19/bin` na frente do PATH, exporta as flags do whisper.cpp (abaixo), roda `npm ci` se faltar `node_modules`, depois `npx tauri build --runner cargo-xwin --target x86_64-pc-windows-msvc --bundles nsis`, e imprime o caminho do instalador.
3. Saída: `target/x86_64-pc-windows-msvc/release/bundle/nsis/PointSpeak_<versão>_x64-setup.exe` (target dir do workspace, na raiz). Confira com `file`: o instalador sai como `PE32 executable (GUI) Intel 80386 ... Nullsoft Installer self-extracting archive` (o stub do NSIS é sempre 32 bits, normal) e o app dentro dele, `target/x86_64-pc-windows-msvc/release/pointspeak.exe`, como `PE32+ executable (GUI) x86-64, for MS Windows`. O esqueleto gerava um instalador de ~2,9 MiB; com o whisper.cpp (task #765) o instalador tem ~4,0 MiB e o `pointspeak.exe` ~6,1 MiB (era ~4,5 MiB).

- **whisper.cpp no .exe (task #765):** o `whisper-rs-sys` compila o whisper.cpp com cmake pelo `clang-cl` do cargo-xwin e repassa as variáveis `GGML_*`/`CMAKE_*` do ambiente ao cmake. O `build-windows.sh` exporta (só se não vierem definidas):
  - `GGML_NATIVE=OFF` (nada de `-march` da máquina de build), `GGML_OPENMP=OFF` (sem DLL do OpenMP) e `GGML_AVX=ON GGML_AVX2=ON GGML_FMA=ON GGML_F16C=ON`.
  - `CMAKE_C_FLAGS_RELEASE`/`CMAKE_CXX_FLAGS_RELEASE=/MT /O2 /Ob2 /DNDEBUG`: STL estática (`libcpmt`). Com o `/MD` padrão o .exe importava o `MSVCP140.dll` (VC++ Redistributable), que o instalador não traz. O resto do app segue o "CRT híbrido" do Tauri (`static_vcruntime`: `libcmt` + `libvcruntime` estáticos, UCRT do sistema). Não use `-C target-feature=+crt-static`: o cargo-xwin tira o UCRT dinâmico, o Tauri tira o estático, e o link falha (`undefined symbol: __stdio_common_vsprintf`, `cos`...).
  - Clang 19: a STL do MSVC baixada pelo xwin recusa o clang 18 do Ubuntu 24.04 (`error STL1000: Unexpected compiler version, expected Clang 19.0.0 or newer`). O cargo-xwin cria o `clang-cl` a partir do primeiro `clang` do PATH, por isso o `/usr/lib/llvm-19/bin` na frente. O cargo-xwin também usa o gerador Ninja no cmake (`ninja-build`).
  - DLLs importadas pelo `pointspeak.exe` (`llvm-objdump -p target/x86_64-pc-windows-msvc/release/pointspeak.exe | grep 'DLL Name'`): só do sistema — `kernel32`, `user32`, `gdi32`, `advapi32`, `shell32`, `ole32`, `oleaut32`, `combase`, `comctl32`, `dwmapi`, `imm32`, `shlwapi`, `ws2_32`, `bcrypt`, `bcryptprimitives`, `ntdll` e os `api-ms-win-crt-*`/`api-ms-win-core-*` (UCRT, parte do Windows 10/11). Nenhuma do VC++ Redistributable; o WebView2 vem do runtime do sistema.
  - O whisper.cpp só entra no .exe porque o app referencia a engine (comando `load_transcriber`); sem nenhuma chamada o LTO o descartaria inteiro.
  - **Limitação: CPU com AVX2** (Intel Haswell 2013+, AMD Excavator/Zen). Numa CPU sem AVX2/FMA o .exe fecha com instrução ilegal ao transcrever. Builds para CPUs antigas: `GGML_AVX2=OFF GGML_FMA=OFF ./scripts/build-windows.sh` (mais lento). GPU (CUDA/Vulkan) fica fora do .exe.
  - Tempos e espaço (8 núcleos): build Windows com whisper.cpp do zero ~2 min (o CRT/SDK do xwin já em cache); `target/x86_64-pc-windows-msvc/` ~1,8 GB, `target/release/` ~1,7 GB (deps de host + o exemplo em release), `~/.cache/cargo-xwin` ~1,1 GB, `clang-19` ~0,2 GB pelo apt.
- **WebView2:** `bundle.windows.webviewInstallMode = embedBootstrapper` no `tauri.conf.json`: o bootstrapper vai dentro do instalador, que instala o WebView2 se faltar. O bootstrapper ainda baixa o runtime da Microsoft; num Windows 10/11 atualizado o WebView2 já vem instalado e nada é baixado.
- **Avisos esperados no build:** `Cross-platform compilation is experimental`, `skipping signing the installer`, `lld-link: Cannot use debug info for 'libcmt.lib(...)' [LNK4099]` (o CRT da Microsoft não traz os .pdb) e `warning 5202: -OUTPUTCHARSET` do makensis. Nenhum impede o instalador.
- **Sem assinatura de código:** o Windows SmartScreen mostra "O Windows protegeu o computador" ao abrir o .exe. É esperado; clique em "Mais informações" → "Executar assim mesmo".
- **Cache do xwin:** o cargo-xwin baixa o CRT do MSVC e o Windows SDK para `~/.cache/cargo-xwin` (fora do repositório; não versione). O primeiro build baixa isso; os seguintes reaproveitam.
- **Espaço em disco:** medido no esqueleto (task #754): `target/x86_64-pc-windows-msvc/` ~0,8 GB, `target/release/` ~0,45 GB (build scripts e proc-macros do host, compilados em release) e `~/.cache/cargo-xwin` ~1,1 GB (só uma vez por máquina). Total ~2,4 GB, fora o `target/debug` dos checks (~4 GB). Primeiro build: ~4 min (inclui baixar o CRT/SDK). Se faltar espaço, apague só `target/x86_64-pc-windows-msvc/debug` (se existir) ou o `target/x86_64-pc-windows-msvc/` inteiro, nunca o cache do xwin à toa.
- **Limitações:** validado o esqueleto (Tauri + bandeja + atalho global) e, desde a task #763, o `cpal` (WASAPI); desde a task #764, o `reqwest` com `rustls`/`ring` (o instalador passou a ~3,5 MiB). desde a task #765, o whisper.cpp (`whisper-rs`, estático, CPU AVX2). O ONNX Runtime (`ort`) ainda não entra; o build cruzado dele será validado na fase de aceleração, que precisa manter este script funcionando. O .exe só é testado de verdade num Windows (manual, pelo dono).

## Como rodar os testes
Na ordem (o `dist/` do `npm run build` é exigido pelo `generate_context!` do Tauri ao compilar o Rust):

```sh
npm ci
npm run lint
npm test                 # no runner: RUNNER_TEST_MAX_WORKERS=2 npm test
npm run build            # tsc --noEmit && vite build
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

- Primeira compilação com o whisper.cpp (task #765, 8 núcleos, `target/` vazio): `cargo build --workspace --all-targets` ~1 min 40 s (o whisper.cpp sai otimizado mesmo em debug); `target/debug` passa a ~7,6 GB. Os checks continuam terminando sozinhos: nenhum teste carrega modelo (o teste real é `#[ignore]`).
- Testes afetados enquanto itera: `npx vitest run --changed origin/main`; só o núcleo: `cargo test -p pointspeak-core`.
- O `vite.config.ts` lê `RUNNER_TEST_MAX_WORKERS` (número ou percentual; padrão `50%`).
- Nenhum teste usa tela, microfone ou rede.
