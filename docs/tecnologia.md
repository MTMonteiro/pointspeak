# Tecnologia: Pointspeak

**Tipo de software:** desktop (Windows e Linux), utilitário de bandeja.

## Stack
- **Linguagens:** Rust (edition 2021) e TypeScript (strict).
- **App desktop:** Tauri v2 (`src-tauri/`), com `tauri-plugin-global-shortcut` e ícone na bandeja (feature `tray-icon`).
- **Frontend:** React 18 + Vite + Tailwind CSS v4 (plugin `@tailwindcss/vite`). Uma página por janela: `hud.html` e `settings.html`.
- **Núcleo:** `crates/pointspeak-core`, Rust puro sem dependências de sistema (`serde`, `serde_json`, `thiserror`, `rubato`, `realfft` e `sha2`): máquina de estados do HUD, contrato dos eventos, configuração, lógica do atalho (PTT/Toggle), pipeline de áudio, Model Manager (catálogos ggml e ONNX e download verificado), o contrato da transcrição (trait `Transcriber` e limpeza do texto), o núcleo puro do Whisper em ONNX (log-mel, vocabulário e decodificação gulosa) e a escolha da engine por backend com o fallback para o whisper.cpp (`engine.rs`).
- **Configuração:** `AppConfig` em `app_config_dir()/config.json` (JSON camelCase; `~/.config/com.pointspeak.app/` no Linux, `%APPDATA%\com.pointspeak.app\` no Windows). Escrita atômica (arquivo `.tmp` + rename). Arquivo ausente ou corrompido carrega os padrões (com log no stderr); campo inválido volta ao padrão e os demais são mantidos. Comandos Tauri: `get_config` e `set_config(config)` (valida, grava e devolve o erro em PT-BR).
- **Eventos backend → HUD:** `hud://state-changed` com `{ state: "idle|recording|transcribing|success|error", message?: string, anchor?: "start|end|center" }` (`message` só no erro, texto curto do `docs/design/DESIGN.md` §3; `anchor` é o `data-anchor` da pílula, reemitido pelo `HudController` quando muda; ausente = manter a última, inicialmente `start`) e `hud://audio-level` com `{ level: 0..1 }`. Constantes e payloads em `pointspeak-core/src/events.rs`.
- **Áudio (em memória, nunca vai para o disco):** `cpal` 0.18 no `src-tauri/src/audio.rs` (ALSA no Linux via `libasound2-dev`, WASAPI no Windows) e `rubato` 5 no núcleo (`pointspeak-core/src/audio.rs`).
  - Captura: `AudioRecorder::from_config(&AppConfig).start(device, on_level, on_auto_stop)` (ou `start_with_classifier(device, Some(classificador do VAD), …)`, que o ditado usa) → `RecordingHandle::stop() -> RecordedAudio` (`samples` 16 kHz mono + `heard_speech`: o detector de silêncio ouviu voz, pelo VAD quando ele está ativo; `None` com a parada por silêncio desligada). `on_auto_stop(Option<StopReason>)` recebe o motivo (`None` = microfone perdido). Usa o formato padrão do dispositivo (f32/i16/u16). O callback do cpal só converte para f32 e faz `try_send` num canal limitado; o processamento roda numa thread própria.
  - Pipeline (`CapturePipeline`): downmix para mono (média) → resample FFT síncrono (`rubato::Fft`, blocos de 1024 quadros, atraso do filtro descartado e resto processado no fim; saída = `ceil(n × 16000 / taxa)`) → RMS a cada 30 ms → `level` 0..1 em escala dB (-60 dB → 0, -10 dB → 1; o `hud://audio-level` continua no RMS) → `SilenceStop` (Silero VAD ou RMS) → buffer limitado a `maxRecordingSecs`.
  - Parada por silêncio (`autoStopOnSilence`, `silenceTimeoutMs`): **Silero VAD** quando o ONNX Runtime e o modelo estão disponíveis, **RMS** de reserva (veja **Silero VAD** abaixo). As duas seguem a mesma regra: só arma depois de 90 ms contínuos de fala e dispara após `silenceTimeoutMs` seguidos de silêncio; fala no meio zera a contagem. Sem relógio real: a duração vem do número de amostras. No RMS (`SilenceDetector`), fala = janela de 30 ms acima de -40 dBFS.
  - Ao atingir `maxRecordingSecs` o buffer para de crescer e o pipeline sinaliza parada; microfone desconectado também chama `on_auto_stop` (e `RecordingHandle::device_lost()` fica `true`).
  - Erros (`AudioError`) viram `ErrorKind::MicrophoneUnavailable` no HUD e texto PT-BR na interface. Comando Tauri `list_microphones` → `[{ name, isDefault }]` (o `name` é o valor de `AppConfig.microphone`).
- **Model Manager (download de modelos):** catálogo, estados e download verificado em `pointspeak-core/src/models.rs` (`sha2`); transporte e comandos em `src-tauri/src/models.rs` (`reqwest` 0.12 blocking com `rustls-tls`/ring, sem OpenSSL nem aws-lc; o Tauri traz o reqwest 0.13 por conta própria).
  - Catálogo: `ggml-tiny.bin`, `ggml-base.bin`, `ggml-small.bin`, `ggml-large-v3-turbo.bin` de `https://huggingface.co/ggerganov/whisper.cpp/resolve/main/<arquivo>`, com tamanho em bytes e SHA-256 tirados do `oid sha256` do LFS (`https://huggingface.co/api/models/ggerganov/whisper.cpp/tree/main`). Textos e tamanhos exibíveis do `DESIGN.md` §4.2; `base` é o recomendado.
  - Pasta: `app_data_dir()/models` (`~/.local/share/com.pointspeak.app/models` no Linux, `%APPDATA%\com.pointspeak.app\models` no Windows). O scan (na inicialização e a cada `list_models`) só confere o tamanho do arquivo; o hash é conferido no download.
  - Download (`download_verified`): consome um `Read`, grava em `<arquivo>.part`, calcula o SHA-256 enquanto grava, avisa o progresso a cada 1 % ou 250 ms, checa a flag de cancelamento a cada bloco de 64 KiB e só renomeia para o nome final com tamanho e hash certos. Em erro ou cancelamento o `.part` é apagado. Mensagens: `Download falhou: conexão perdida` (leitura falhou ou o stream acabou antes), `Arquivo corrompido (SHA-256 não confere)` (hash ou tamanho a mais), `Não foi possível gravar o modelo: …` (disco). Uma thread por download; timeout de 30 s para conectar e para cada leitura.
  - Estados por modelo (`ModelState`, JSON `{ "state": … }`): `notDownloaded`, `downloading` (`done`, `total`), `verifying`, `ready`, `active` (o `AppConfig.model`, se o arquivo existe), `failed` (`reason`).
  - Comandos Tauri: `list_models` → `{ models: [{ id, fileName, sizeBytes, sha256, displaySize, description, recommended, state, done?, total?, reason? }], dir, usedBytes }`; `download_model({ id })` (volta na hora; um por vez por modelo); `cancel_download({ id })`; `remove_model({ id })` (recusa o ativo com "Troque o modelo ativo antes de remover" e o que está baixando); `set_active_model({ id })` (precisa estar `ready`; grava `AppConfig.model` e devolve a config). A pasta abre pelo `open_models_dir` (veja **Janela de Configurações** abaixo).
  - Evento `models://progress` com `{ id, state, done, total, reason? }` a cada mudança (constante e payload em `pointspeak-core/src/events.rs`).
  - Variantes (task #794): os comandos e o evento usam a variante da engine do backend efetivo (ggml para CPU/Vulkan, ONNX para DirectML/OpenVINO/CUDA; veja **Engine Whisper ONNX** abaixo). Veja lá o que muda nos valores.
- **Transcrição (whisper.cpp):** contrato em `pointspeak-core/src/transcriber.rs`, engine em `src-tauri/src/transcriber.rs` (`whisper-rs` 0.16 → whisper.cpp 1.8, compilado do fonte pelo `whisper-rs-sys` com cmake e linkado estático).
  - Trait `Transcriber: Send` (`transcribe(&mut self, audio: &[f32], opts) -> Result<String, TranscribeError>` e `name()`), sem nada de whisper: a engine ONNX (`OrtWhisperTranscriber`, task #794) implementa o mesmo. `TranscribeOptions { language: pt|en|auto }` (`TranscribeOptions::from_config`).
  - Quem chama usa `pointspeak_core::transcriber::transcribe(engine, audio, opts)`: áudio vazio ou com menos de 300 ms (4800 amostras a 16 kHz) devolve `""` sem chamar a engine; o texto sai limpo (`clean_text`/`join_segments`: trim, segmentos juntados com espaço, tudo entre `[]` removido — `[BLANK_AUDIO]`, `[Music]`, `[ Silence ]` —, marcadores conhecidos entre `()`/`**` como `(música)`, `(risos)`, `*music*`, notas `♪`, espaços duplos e espaço antes de pontuação). Parênteses de texto normal ficam.
  - Erros (`TranscribeError`, mensagens PT-BR): `NoModelSelected` e `ModelNotFound(caminho)` → `ErrorKind::ModelNotFound`; `Load` e `Inference` → `ErrorKind::TranscriptionFailed`.
  - `WhisperTranscriber::load(caminho)`: confere o arquivo (ausente → `ModelNotFound`), cria o `WhisperContext` e um `WhisperState` reaproveitado em todo ditado. Inferência greedy (`best_of: 1`), `set_language("pt"|"en"|"auto")` (`auto` detecta; `set_detect_language` não é usado porque só detectaria sem transcrever), `no_context`, sem timestamps, `suppress_blank`/`suppress_nst`, threads = `min(núcleos físicos, 8)` (`num_cpus`).
  - Logs: `whisper_rs::install_logging_hooks()` (feature `log_backend`) tira os logs do whisper.cpp/GGML do stdout e os manda para o crate `log`; um logger mínimo do app repassa só avisos e erros ao stderr com o prefixo `[pointspeak]`. Se outro logger for instalado antes (fase de qualidade), ele recebe tudo.
  - Estado: `AppState.transcriber: Mutex<EngineSlot>` (o `EngineSlot` do núcleo guarda o `Option<Box<dyn Transcriber>>` e a `EngineKey` = modelo + backend efetivo; desde a task #794, antes era o caminho do `.bin`). `transcriber::ensure_loaded(app, &config)` carrega no primeiro uso e, se o modelo ativo ou o backend mudou (hot-swap), **libera o contexto antigo antes** de carregar o novo; se o carregamento falhar o slot fica vazio. `transcriber::transcribe(app, &config, &audio)` faz `ensure_loaded` + transcrição. Comando Tauri `load_transcriber` (sem argumentos): pré-carrega o modelo ativo numa thread de bloqueio e devolve o erro em PT-BR (gancho para a pré-carga da fase 4 e para as telas). Carregamento lazy por enquanto; eager/lazy configurável fica para a fase 4.
  - Features do crate `pointspeak` (desligadas por padrão, fora do .exe): `cuda` e `vulkan` (repassam a `whisper-rs/cuda`/`whisper-rs/vulkan` e ligam `use_gpu`). Precisam do CUDA Toolkit / Vulkan SDK na máquina de build.
  - Exemplo: `cargo run -p pointspeak --release --example transcribe -- [--backend <cpu|directml|openvino|cuda>] <modelo.bin | pasta onnx-<id>> <audio.wav> [pt|en|auto]` (padrão `auto` e `cpu`; pasta = engine ONNX, veja **Engine Whisper ONNX**). Lê o WAV com `hound` (dev-dependency; inteiro ou float, qualquer taxa/canais), faz downmix e resample para 16 kHz pelo `pointspeak_core::audio` e imprime o texto no stdout e os tempos no stderr. Em debug o whisper.cpp já sai otimizado (o `whisper-rs-sys` compila em `RelWithDebInfo`), mas use `--release` para medir.
  - Validado (task #765) com `ggml-tiny.bin` e o `samples/jfk.wav` do whisper.cpp (11 s): `en` e `auto` → "And so my fellow Americans ask not what your country can do for you ask what you can do for your country." em ~0,55 s (`en`) e ~1,5 s (`auto`, inclui a detecção) com 8 threads; modelo carregado em ~0,1 s. O mesmo áudio a 48 kHz estéreo deu o mesmo texto (resample do núcleo). Teste real opcional: `POINTSPEAK_TEST_MODEL=… POINTSPEAK_TEST_WAV=… cargo test -p pointspeak --lib whisper_real -- --ignored` (WAV 16 kHz mono i16).
- **HUD que segue o cursor (task #772):** geometria pura em `pointspeak-core/src/hud_layout.rs`, janela em `src-tauri/src/hud.rs` (`HudController`, estado gerenciado do Tauri registrado no `setup`; mostrado/escondido pelo executor do ditado).
  - Unidades: o Tauri 2 dá o cursor (`AppHandle::cursor_position`), os monitores (`available_monitors`: posição, tamanho, `work_area`, `scale_factor`) e posiciona a janela (`set_position(PhysicalPosition)`) em pixels **físicos**. As medidas do design (220 × 56, margem 8, 48 no Wayland) são **lógicas** e são convertidas pelo `scale_factor` do monitor do cursor (`round(lógico × escala)`). Cursor fracionário arredonda para baixo.
  - Regra (DESIGN §3.1): janela em `cursor + 8`; se passar da borda direita da `work_area`, `x = cursor.x − 8 − largura` e âncora `end`; o mesmo em `y` com a altura; no fim a janela é presa dentro da `work_area`. O monitor é o que contém o cursor (`monitor_index_at`), ou o mais próximo; o `monitor_from_point` do Tauri não é usado porque no Linux repassa o ponto ao GDK, que espera coordenadas lógicas.
  - Decisão da API de cursor: só a API do Tauri (sem `x11rb` nem `rdev`). No X11 o tao lê o ponteiro pelo GDK; no Windows pelo `GetCursorPos`. A crate `windows` 0.62 (a mesma do Tauri, só em `cfg(windows)`) entra só para mostrar sem ativar.
  - Rastreio: uma thread (`pointspeak-hud-tracker`) criada no primeiro `show()`, chama o tick a cada 16 ms (~60 Hz) enquanto o HUD está visível e fica estacionada em `thread::park` quando escondido (sem girar). A lista de monitores é relida a cada 1 s durante o rastreio; a janela só é movida quando a posição muda.
  - Foco e click-through: `focusable: false` vira `accept_focus(false)` no GTK (X11 não dá foco no `show()`) e `WS_EX_NOACTIVATE` no Windows. Mas o `show()` do tao no Windows usa `ShowWindow(SW_SHOW)`, que ativa; por isso no Windows o HUD é mostrado com `ShowWindow(SW_SHOWNOACTIVATE)` + `SetWindowPos(HWND_TOPMOST, SWP_NOACTIVATE)` e escondido com `SW_HIDE`, direto no hwnd (nunca pelo `show()`/`hide()` do Tauri, cuja flag interna fica "escondida"). Click-through: `set_ignore_cursor_events(true)` (no Windows antes de mostrar; no Linux depois, porque o tao precisa do `GdkWindow` já realizado).
  - Wayland (`DisplayServer::detect_from_env`: `GDK_BACKEND` primeiro, depois `WAYLAND_DISPLAY`, depois `XDG_SESSION_TYPE`): sem posição global do cursor (o tao devolve `(0, 0)`). O HUD é posto uma vez no `show()`, no centro-inferior da `work_area` do monitor principal, sem rastreio. **Limitação:** janela comum (sem layer-shell), o compositor pode ignorar a posição pedida. Com `GDK_BACKEND=x11` o app roda no XWayland e segue o cursor (só enquanto ele está sobre janelas X11).
- **Injeção de texto (task #773):** regras puras em `pointspeak-core/src/injector.rs`, efeito em `src-tauri/src/injector.rs` (`injector::inject(texto, display) -> Result<(), InjectError>`; chamado pelo executor do ditado numa thread `pointspeak-inject`).
  - Dependências: `arboard` 3.7 (clipboard de texto e imagem; no Linux via X11/XWayland, sem a feature `wayland-data-control`), `enigo` 0.6 (teclas; no Linux o backend padrão `x11rb`/XTest, sem libxdo; o `xkbcommon` dele linka a `libxkbcommon`, agora no `setup-linux.sh`), `x11rb` 0.13 só no Linux (janela ativa) e as features `Win32_System_Threading` da crate `windows` (processo da janela em primeiro plano).
  - Sequência (spec §4.6, `paste_preserving_clipboard` sobre o trait `ClipboardLike`): texto vazio ou só espaços não cola nem toca o clipboard → guarda o clipboard (texto; senão imagem RGBA; senão "vazio") → põe o texto → cola → espera `RESTORE_DELAY` (50 ms) → restaura (vazio = limpa). **Colagem falhou:** tenta restaurar o clipboard original antes de devolver `ErrorKind::PasteFailed` ("Falha ao colar"); falha ao restaurar após colagem bem-sucedida conta como sucesso, com aviso no log.
  - Atalho (`paste_keys_for`): Shift+Insert se o app em foco é um terminal da lista fixa `TERMINALS` (comparação sem maiúsculas: gnome-terminal(-server), konsole, xterm, alacritty, kitty, wezterm/org.wezfurlong.wezterm, terminator, tilix, xfce4-terminal, urxvt/rxvt, foot, WindowsTerminal.exe, cmd.exe, conhost.exe, powershell.exe, pwsh.exe, mintty.exe); qualquer outro app ou nada detectado → Ctrl+V. App em foco: Windows `GetForegroundWindow` → `GetWindowThreadProcessId` → `QueryFullProcessImageNameW` (nome do executável); X11 `_NET_ACTIVE_WINDOW` → `WM_CLASS` (instância e classe); Wayland não detecta.
  - Métodos por servidor gráfico (`paste_strategy`, o primeiro que funcionar vale): Windows e X11 = enigo (SendInput / XTest; Ctrl+V usa a tecla virtual V no Windows e o keysym `v` no X11); Wayland = `wtype -M ctrl v -m ctrl` (Shift+Insert: `-M shift -k Insert -m shift`) → `ydotool key 29:1 47:1 47:0 29:0` (Shift+Insert: `42:1 110:1 110:0 42:0`) → enigo (só alcança apps do XWayland). `wtype`/`ydotool` são procurados no `PATH`; ausente ou saída com erro passa ao próximo, e o erro final junta os motivos.
  - Thread: arboard e enigo bloqueiam, então tudo roda na thread `pointspeak-injector` (criada na primeira chamada; `inject` manda o trabalho por canal e espera a resposta, então chame fora da thread principal). Ela mantém o `Clipboard` e o `Enigo` vivos: no X11 o conteúdo do clipboard só existe enquanto o processo que o pôs o serve.
  - **Limitações:** conteúdo do clipboard que não é texto nem imagem (arquivos copiados, HTML/RTF sem texto puro) não é guardado e o clipboard fica vazio depois da colagem; texto com formatação volta só como texto puro. No Wayland a colagem exige `wtype` (compositores com `virtual-keyboard`, ex. wlroots/KDE; o GNOME não tem) ou `ydotool` com o daemon `ydotoold` rodando (acesso ao `/dev/uinput`); sem detecção do app em foco, terminais nativos do Wayland recebem Ctrl+V. No Windows, janelas de processos elevados (admin) não recebem as teclas (UIPI) e não têm o processo detectado.
  - **Modo `clipboard` (`outputMode`, Configurações → Saída):** `deliver(text, display, mode)` com `OutputMode::Clipboard` só põe o texto no clipboard (`copy_to_clipboard`, núcleo), na mesma thread e com o `Clipboard` vivo (no X11 o texto só existe enquanto o app o serve); não simula teclas, não espera e não restaura o conteúdo anterior. Texto vazio não toca o clipboard (o ditado já vira `NoSpeech` antes). Falha vira `ErrorKind::PasteFailed`. O `outputMode` é lido a cada ditado; config antigo sem o campo cola (`paste`).
  - Teste manual (com tela): `cargo run -p pointspeak --example inject -- "texto"` espera 3 s (foque o app de destino) e cola. Nenhum teste dos checks toca o clipboard real ou simula teclas: a sequência é testada com um clipboard falso no núcleo.
- **Ditado ponta a ponta (task #774):** máquina pura em `pointspeak-core/src/dictation.rs`, executor em `src-tauri/src/dictation.rs`, atalho em `src-tauri/src/shortcut.rs`, bandeja em `src-tauri/src/tray.rs`.
  - Fluxo: atalho (Pressed/Released do `tauri-plugin-global-shortcut`) → `Input::Hotkey` → `HotkeyController` (PTT/Toggle, autorepeat, PTT < 300 ms cancela) → `StartRecording` + `hud://state-changed` `recording` + `ShowHud` → `hud://audio-level` a cada janela de 30 ms (direto do callback do medidor) → parada (release/segundo toque/silêncio/duração máxima) → `StopRecording` + `transcribing` + `Transcribe` → texto → `Inject` → `success` (some em 400 ms) ou `error` com a mensagem do `ErrorKind` (some em visível + 400 ms de fade: 3000 ms microfone/modelo/transcrição, 4000 ms colagem, 2000 ms sem fala) → `idle` + `HideHud`.
  - Sem fala (o detector nunca ouviu voz, áudio vazio/< 300 ms ou texto vazio depois da limpeza) → erro `Nada foi ouvido`, sem chamar a engine (quando dá) e sem colar. Microfone que não abre → `RecordingFailed`; que cai no meio → `DeviceLost`: os dois mostram `Microfone indisponível`.
  - Threads: um só dono do estado, a thread `pointspeak-dictation`, com um canal `mpsc` de entradas; ela aplica a máquina e executa os efeitos na ordem (trait `Backend`: `TauriBackend` no app, fake nos testes). A gravação usa as threads do `audio.rs`; a inferência roda em `pointspeak-transcribe` (uma por ditado) e a colagem em `pointspeak-inject`, que respondem pelo canal. O timer de dispensa é o `recv_timeout` do laço; entrada fora de hora (atalho durante a transcrição, `AutoStop` de gravação anterior, timer vencido depois da pausa) é ignorada. Nada roda na thread principal.
  - Atalho: `config.hotkey` é registrado no `setup` (`shortcut::to_shortcut(&Accelerator) -> Shortcut`). `set_config` (síncrono, na thread principal) registra o novo **antes** de soltar o antigo; se o SO recusar, devolve `"<atalho> já é usado por outro app ou pelo sistema. Escolha outra combinação."` e mantém o anterior (nada é gravado). O plugin registra na thread principal e bloqueia até ela responder, por isso o `HotkeyBinding` só é usado nela (o executor posta a pausa com `run_on_main_thread`, sem esperar).
  - Bandeja (DESIGN §5): `PointSpeak — <estado>` desabilitado (o mesmo texto no tooltip) com `Pronto (Alt+Z)`, `Gravando…`, `Transcrevendo…`, `Pausado`, `Carregando modelo…`, `Nenhum modelo ativo — abra as Configurações`; `Pausar ditado`/`Retomar ditado` (solta/registra o atalho; o modelo continua carregado; pausar no meio da gravação a descarta); `Configurações…`; `Sair`. Clique esquerdo abre as Configurações no Windows (no Linux o appindicator não entrega o clique e só abre o menu). Ícones por estado ficam para o empacotamento.
  - Modelo: no `setup`, se `config.model` estiver definido, `dictation::reload_model` carrega em segundo plano (`pointspeak-model-load`, bandeja em `Carregando modelo…`); `set_active_model` e `set_config` com modelo diferente recarregam. Ditado sem engine carregada carrega na hora (lazy, dentro do `transcribe`).
  - Comandos que mudaram: `set_config` também troca o atalho e avisa o ditado (modo, texto da bandeja, modelo). Nenhum comando novo nesta task (os da janela de Configurações vieram na #781).
  - Validação manual: `docs/checklist-manual.md` (Windows .exe e Linux X11/Wayland).
- **Janela de Configurações: comandos e eventos (task #781):** lógica pura em `pointspeak-core/src/settings.rs`, comandos em `src-tauri/src/settings.rs` (e `suspend_hotkey` em `src-tauri/src/shortcut.rs`); nomes e payloads em `pointspeak-core/src/events.rs`. Erros saem como string em PT-BR. Nenhuma dependência nova.
  - Motor: `get_engine_status` → `{ model: ModelId|null, status: "notSelected|loading|loaded|failed", backend, paused, fallbackReason? }` (camelCase; `fallbackReason` desde a task #794, veja **Engine Whisper ONNX**); o mesmo payload sai no evento `engine://status`, só para a janela `settings`, a cada mudança do estado do modelo ou da pausa (o executor do ditado compara depois de cada entrada e chama `Backend::engine_changed`; um ditado não emite) e quando o `set_config` troca o backend. `backend` é o que roda de fato: o efetivo (`effective_backend`: `auto` e backend indisponível caem no primeiro disponível com engine, na ordem dos cartões) ou a CPU depois de um fallback da engine ONNX. Os textos do rodapé (`Pronto · base · CPU`, `Carregando modelo…`, `Nenhum modelo ativo`) ficam com o frontend.
  - Hardware: `list_backends` (assíncrono, fora da thread principal) → `[{ backend, available, reason?, detail? }]` para `directml, openvino, vulkan, cuda, cpu`, de `backend_options(TargetOs, &HardwareProbe)` sobre a detecção real (veja **ONNX Runtime** abaixo). Motivos (DESIGN.md §4.2): DirectML fora do Windows `Disponível só no Windows`; DirectML/OpenVINO/CUDA sem biblioteca `ONNX Runtime não encontrado`, biblioteca que não carrega `ONNX Runtime não pôde ser carregado`; EP ausente ou que não inicia: DirectML `Nenhuma GPU ou NPU compatível com DirectML` (texto novo, fora do design), OpenVINO `Nenhum dispositivo Intel compatível`, CUDA `Nenhuma GPU NVIDIA encontrada`; Vulkan `Não incluído nesta versão` (sem a feature `vulkan`) ou `Driver Vulkan não encontrado` (feature ligada, loader `libvulkan.so.1`/`vulkan-1.dll` ausente). `detail` = fabricante do dispositivo quando o ONNX Runtime lista um para a EP (senão omitido); CPU `Sempre disponível`.

Medido na task #806 (0.1.0): **.deb 13,3 MiB** (13.986.562 bytes; instalado ~32 MB) e **AppImage 87,4 MiB** (91.691.512 bytes; o linuxdeploy embute GTK/WebKit e dependências). O `libonnxruntime.so` sozinho tem 21 MiB.

- **Overlay `src-tauri/tauri.onnxruntime-linux.conf.json`:** mesmo padrão do Windows: só o `build-linux.sh` o passa por `--config`, então o `cargo build` e o `generate_context!` dos checks não exigem o arquivo. Põe `libonnxruntime.so` na raiz dos recursos e a licença em `licenses/onnxruntime-LICENSE.txt` (o mapa soma com o do `tauri.conf.json`, que já traz o Silero VAD). Só a CPU EP: o pacote oficial `onnxruntime-linux-x64` não traz CUDA nem OpenVINO, e nada disso entra no pacote.
- **Onde o app acha a biblioteca:** a `resource_dir()` do Tauri no Linux é `<pasta do executável>/../lib/<productName>` quando existe; no .deb, `/usr/bin/pointspeak` → `/usr/lib/PointSpeak/`; no AppImage, `$APPDIR/usr/lib/PointSpeak/`. É a segunda opção do `pointspeak_core::onnx_runtime::library_candidates` (depois do `ORT_DYLIB_PATH`), com o nome `libonnxruntime.so`: nada mudou na busca. O teste `crates/pointspeak-core/tests/bundle_resources.rs` confere que os dois overlays põem a biblioteca na raiz dos recursos e que esses caminhos resolvem. Conferido também extraindo o .deb (`dpkg-deb -x`) e abrindo o binário sem `ORT_DYLIB_PATH`: o processo carrega o `usr/lib/PointSpeak/libonnxruntime.so` extraído (`/proc/<pid>/maps`) e imprime `[pointspeak] Silero VAD carregado de …/usr/lib/PointSpeak/resources/silero_vad.onnx` (a sessão do VAD só abre com o ONNX Runtime carregado).
- **Dependências do .deb** (o Tauri não roda `dpkg-shlibdeps`): o padrão do Tauri (`libwebkit2gtk-4.1-0`, `libgtk-3-0` e `libayatana-appindicator3-1`, pela bandeja) mais `bundle.linux.deb.depends` = `libasound2t64 | libasound2` (cpal/ALSA; o nome mudou no Ubuntu 24.04). `libstdc++6`, `libdbus-1-3`, `libsoup-3.0-0` e o resto do `readelf -d` vêm pelo WebKit/GTK. `Recommends: wtype, ydotool` (`bundle.linux.deb.recommends`): colagem no Wayland. O nome do pacote é `point-speak` (o Tauri deriva do `productName`).
- **Limitações:** CPU com AVX2 (como no Windows; `GGML_AVX2=OFF GGML_FMA=OFF ./scripts/build-linux.sh` para CPUs antigas). Sem assinatura do .deb/AppImage. O AppImage foi gerado neste Ubuntu 24.04 e roda em distribuições com glibc igual ou mais nova. O pacote só é testado de verdade instalado numa máquina com tela (manual: `docs/checklist-manual.md`).

## Instalador Windows (.exe NSIS, compilação cruzada)
O instalador Windows sai deste Linux pelo caminho documentado do Tauri v2 (cargo-xwin + `x86_64-pc-windows-msvc` + NSIS). Não entra nos checks (pesado demais); rode nas etapas que mexem em dependência nativa e no empacotamento.

1. Pré-requisitos (uma vez por máquina, depois do `setup-linux.sh`): `./scripts/setup-windows-cross.sh`. Idempotente: instala `nsis lld llvm clang clang-19 ninja-build` pelo apt, `rustup target add x86_64-pc-windows-msvc` e `cargo install --locked cargo-xwin`.
2. Gerar: `./scripts/build-windows.sh`. Põe `/usr/lib/llvm-19/bin` na frente do PATH, exporta as flags do whisper.cpp (abaixo), roda `npm ci` se faltar `node_modules`, depois `npx tauri build --runner cargo-xwin --target x86_64-pc-windows-msvc --bundles nsis`, e imprime o caminho do instalador.
3. Saída: `target/x86_64-pc-windows-msvc/release/bundle/nsis/PointSpeak_<versão>_x64-setup.exe` (target dir do workspace, na raiz). Confira com `file`: o instalador sai como `PE32 executable (GUI) Intel 80386 ... Nullsoft Installer self-extracting archive` (o stub do NSIS é sempre 32 bits, normal) e o app dentro dele, `target/x86_64-pc-windows-msvc/release/pointspeak.exe`, como `PE32+ executable (GUI) x86-64, for MS Windows`. O esqueleto gerava um instalador de ~2,9 MiB; com o whisper.cpp (task #765) o instalador tinha ~4,0 MiB e o `pointspeak.exe` ~6,1 MiB (era ~4,5 MiB). Com o ONNX Runtime (task #791) o instalador tem **16,9 MiB** (17.731.486 bytes) e o `pointspeak.exe` ~7,3 MiB. Com o Silero VAD (task #792) o instalador tem **18,6 MiB** (19.539.942 bytes) e leva `resources\silero_vad.onnx` e `licenses\silero_vad-LICENSE.txt` (o `build-windows.sh` confere o modelo no `installer.nsi`; o `bundle.resources` do `tauri.conf.json` e o do overlay são mapas e se somam). Com a engine Whisper ONNX (task #794) o instalador tem **18,7 MiB** (19.569.766 bytes) e o `pointspeak.exe` ~7,5 MiB (7.861.248 bytes); sem DLL nova (a engine usa o mesmo `onnxruntime.dll`) e o `pointspeak.exe` continua sem import estático do ONNX Runtime.

- **whisper.cpp no .exe (task #765):** o `whisper-rs-sys` compila o whisper.cpp com cmake pelo `clang-cl` do cargo-xwin e repassa as variáveis `GGML_*`/`CMAKE_*` do ambiente ao cmake. O `build-windows.sh` exporta (só se não vierem definidas):
  - `GGML_NATIVE=OFF` (nada de `-march` da máquina de build), `GGML_OPENMP=OFF` (sem DLL do OpenMP) e `GGML_AVX=ON GGML_AVX2=ON GGML_FMA=ON GGML_F16C=ON`.
  - `CMAKE_C_FLAGS_RELEASE`/`CMAKE_CXX_FLAGS_RELEASE=/MT /O2 /Ob2 /DNDEBUG`: STL estática (`libcpmt`). Com o `/MD` padrão o .exe importava o `MSVCP140.dll` (VC++ Redistributable), que o instalador não traz. O resto do app segue o "CRT híbrido" do Tauri (`static_vcruntime`: `libcmt` + `libvcruntime` estáticos, UCRT do sistema). Não use `-C target-feature=+crt-static`: o cargo-xwin tira o UCRT dinâmico, o Tauri tira o estático, e o link falha (`undefined symbol: __stdio_common_vsprintf`, `cos`...).
  - Clang 19: a STL do MSVC baixada pelo xwin recusa o clang 18 do Ubuntu 24.04 (`error STL1000: Unexpected compiler version, expected Clang 19.0.0 or newer`). O cargo-xwin cria o `clang-cl` a partir do primeiro `clang` do PATH, por isso o `/usr/lib/llvm-19/bin` na frente. O cargo-xwin também usa o gerador Ninja no cmake (`ninja-build`).
  - DLLs importadas pelo `pointspeak.exe` (`llvm-objdump -p target/x86_64-pc-windows-msvc/release/pointspeak.exe | grep 'DLL Name'`): só do sistema — `kernel32`, `user32`, `gdi32`, `advapi32`, `shell32`, `ole32`, `oleaut32`, `combase`, `comctl32`, `dwmapi`, `imm32`, `shlwapi`, `ws2_32`, `bcrypt`, `bcryptprimitives`, `ntdll` e os `api-ms-win-crt-*`/`api-ms-win-core-*` (UCRT, parte do Windows 10/11). Nenhuma do VC++ Redistributable; o WebView2 vem do runtime do sistema.
  - O whisper.cpp só entra no .exe porque o app referencia a engine (comando `load_transcriber`); sem nenhuma chamada o LTO o descartaria inteiro.
  - **Limitação: CPU com AVX2** (Intel Haswell 2013+, AMD Excavator/Zen). Numa CPU sem AVX2/FMA o .exe fecha com instrução ilegal ao transcrever. Builds para CPUs antigas: `GGML_AVX2=OFF GGML_FMA=OFF ./scripts/build-windows.sh` (mais lento). GPU (CUDA/Vulkan) fica fora do .exe.
  - Tempos e espaço (8 núcleos): build Windows com whisper.cpp do zero ~2 min (o CRT/SDK do xwin já em cache); `target/x86_64-pc-windows-msvc/` ~1,8 GB, `target/release/` ~1,7 GB (deps de host + o exemplo em release), `~/.cache/cargo-xwin` ~1,1 GB, `clang-19` ~0,2 GB pelo apt.
- **ONNX Runtime no .exe (task #791):** o `build-windows.sh` roda `./scripts/fetch-onnxruntime.sh windows` e passa `--config src-tauri/tauri.onnxruntime-windows.conf.json` ao `tauri build`; o overlay põe em `bundle.resources` o `onnxruntime.dll` (1.24.4, DirectML) e o `DirectML.dll` (1.15.4) na raiz da instalação, ao lado do `pointspeak.exe` (é a `resource_dir()` no Windows), e as licenças em `licenses\`. O nome não é `tauri.windows.conf.json` de propósito: esse o Tauri mescla sozinho em todo build Windows. O script confere no fim que o `pointspeak.exe` não importa o `onnxruntime.dll` (`llvm-objdump -p`, `load-dynamic`) e que as duas DLLs estão no `installer.nsi` gerado. Conferido: imports só do sistema (a lista acima, mais `mmdevapi`), `File /a "/oname=onnxruntime.dll"` e `"/oname=DirectML.dll"` no `target/x86_64-pc-windows-msvc/release/nsis/x64/installer.nsi`; o desinstalador apaga as duas.
- **WebView2:** `bundle.windows.webviewInstallMode = embedBootstrapper` no `tauri.conf.json`: o bootstrapper vai dentro do instalador, que instala o WebView2 se faltar. O bootstrapper ainda baixa o runtime da Microsoft; num Windows 10/11 atualizado o WebView2 já vem instalado e nada é baixado.
- **Avisos esperados no build:** `Cross-platform compilation is experimental`, `skipping signing the installer`, `lld-link: Cannot use debug info for 'libcmt.lib(...)' [LNK4099]` (o CRT da Microsoft não traz os .pdb) e `warning 5202: -OUTPUTCHARSET` do makensis. Nenhum impede o instalador.
- **Sem assinatura de código:** o Windows SmartScreen mostra "O Windows protegeu o computador" ao abrir o .exe. É esperado; clique em "Mais informações" → "Executar assim mesmo".
- **Cache do xwin:** o cargo-xwin baixa o CRT do MSVC e o Windows SDK para `~/.cache/cargo-xwin` (fora do repositório; não versione). O primeiro build baixa isso; os seguintes reaproveitam.
- **Espaço em disco:** medido no esqueleto (task #754): `target/x86_64-pc-windows-msvc/` ~0,8 GB, `target/release/` ~0,45 GB (build scripts e proc-macros do host, compilados em release) e `~/.cache/cargo-xwin` ~1,1 GB (só uma vez por máquina). Desde a task #791, o ONNX Runtime (`ort` `load-dynamic`, DLLs no instalador; a detecção do DirectML só é validada num Windows de verdade). ## Segurança e privacidade
Revisão da task #807 (achados e o que ficou de fora na ficha da task). Garantias que o código mantém:

- **Nada do ditado sai da máquina nem vai para log.** O áudio fica só em memória (`audio.rs`: canal limitado → `RecordingBuffer` com teto de `max_recording_secs`, no máximo 3600 s ≈ 230 MB de f32) e é solto depois da inferência; não há gravação em disco. O texto transcrito e o conteúdo do clipboard nunca entram em `eprintln!`/`log::` (os erros de colagem e de inferência só levam o motivo) nem em evento (o `hud://state-changed` leva só o estado e a mensagem de erro). A única rede do app é o download dos modelos; não há telemetria.
- **Modo `clipboard`:** o texto ditado substitui o clipboard e fica lá até o usuário copiar outra coisa (nada é restaurado); continua marcado para ficar fora do histórico (Win+V/nuvem), então não aparece nele. Qualquer app que leia o clipboard vê o texto.
- **Clipboard do usuário:** guardado (texto ou imagem) antes de colar e restaurado depois dos 50 ms, também quando a colagem falha (`paste_preserving_clipboard`). Cancelar ou errar antes da colagem não toca o clipboard. O texto ditado é marcado para ficar fora do histórico do clipboard (Windows: Win+V e nuvem; Linux: `x-kde-passwordManagerHint`, respeitado pelo Klipper e outros), pelo `SetExtWindows`/`SetExtLinux` do arboard.
- **Downloads de modelo:** URLs fixas em HTTPS (`huggingface.co`, ONNX num commit fixado), `reqwest` com rustls. Cada arquivo é gravado em `.part`, com o tamanho limitado ao do catálogo (byte a mais = corrompido) e o SHA-256 conferido antes do `rename`; `.part` nunca é carregado. Os comandos recebem o modelo como `ModelId` (enum), então não há caminho vindo da interface nem path traversal na pasta dos modelos. O atalho (`Accelerator::parse`) e os limites numéricos são validados no `set_config`.
- **Superfície da interface:** CSP `default-src 'self'` (estilos inline liberados para o React) e permissões por janela: os comandos do app são declarados no `build.rs`, a capability `settings` libera `core:default` e os comandos, a `hud` só `listen`/`unlisten` de eventos (o HUD não invoca comando nem mexe em janela).
- **Scripts de build:** `fetch-onnxruntime.sh` baixa versões fixas e confere o SHA-256 de cada pacote; nenhum script faz `curl | sh`.
- **Robustez:** pânico na thread de inferência ou de colagem vira erro no HUD (o ditado não fica preso em "Transcrevendo…"); a thread do injector sobrevive a um pânico; locks envenenados seguem com o valor (sem `unwrap()` de `Mutex` fora dos testes). Pânico na thread de áudio devolve áudio vazio (o HUD mostra "sem fala"); falha do VAD cai para o RMS.
- **Desempenho ocioso:** sem polling com o app parado: o rastreio do cursor só roda com o HUD visível (thread estacionada com `park`), o executor do ditado e o injector esperam em canal, o timer do HUD só corre gravando. O callback do `cpal` não bloqueia (`try_send`; bloco descartado se a fila de ~5 s encher) e a fila do VAD é limitada. O hot-swap solta a engine antiga antes de carregar a nova.

Riscos aceitos:

- **Busca do ONNX Runtime:** `ORT_DYLIB_PATH` → `resource_dir` → pasta do executável. Quem controla o ambiente do usuário consegue carregar outra biblioteca pela variável; isso pressupõe acesso à conta, então é aceito (a variável existe para desenvolvimento). Caminho relativo na variável é ignorado (seria resolvido pela pasta atual). No Windows o `DirectML.dll` é pré-carregado da pasta do `onnxruntime.dll` (não o antigo do System32); as demais dependências do ONNX Runtime seguem a ordem de busca padrão do Windows, que começa pela pasta do executável. O instalador NSIS é por usuário, então a pasta da instalação é gravável pelo próprio usuário (como em todo app instalado por usuário).
- **Clipboard compartilhado por 50 ms:** outro app que leia o clipboard nesse intervalo vê o texto ditado; gerenciadores que ignoram as dicas de histórico podem guardá-lo.
- **Callback do `cpal`** aloca um `Vec<f32>` por bloco (conversão de formato): não bloqueia, mas não é livre de alocação.
- **Sem assinatura** do instalador nem dos pacotes Linux; integridade só pelo canal de distribuição.

## Como rodar os testes
Na ordem (o `dist/` do `npm run build` é exigido pelo `generate_context!` do Tauri ao compilar o Rust):

```sh
npm ci
npm run lint
npm test                 # no runner: RUNNER_TEST_MAX_WORKERS=2 npm test
npm run build            # tsc --noEmit && vite build
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

- Primeira compilação com o whisper.cpp (task #765, 8 núcleos, `target/` vazio): `cargo build --workspace --all-targets` ~1 min 40 s (o whisper.cpp sai otimizado mesmo em debug); `target/debug` passa a ~7,6 GB. Os checks continuam terminando sozinhos: nenhum teste carrega modelo (o teste real é `#[ignore]`).
- Testes afetados enquanto itera: `npx vitest run --changed origin/main`; só o núcleo: `cargo test -p pointspeak-core`.
- Testes de integração do núcleo (`crates/pointspeak-core/tests/`) cobrem áudio sintético até ditado/transcrição/colagem, config/modelos, fallbacks e clipboard falso; não usam tela, microfone, rede, modelos ou ONNX Runtime.
- O contrato Rust↔TypeScript fica em `src/test/fixtures/rust-contracts.json`. `cargo test --workspace` compara a fixture serializada; o Vitest a lê em `src/test/rust-contract.test.tsx` e exercita HUD e Settings. Para regenerar após revisar uma mudança intencional de contrato: `cargo test -p pointspeak-core --test contract_fixtures write_rust_contract_fixtures -- --ignored`.
- O `vite.config.ts` lê `RUNNER_TEST_MAX_WORKERS` (número ou percentual; padrão `50%`).
- Nenhum teste usa tela, microfone ou rede.
